# v0.41.0-beta.1 Version Plan - Adoption Freeze

## Objective

Turn the alpha.6 architecture hardening and alpha.7 desktop dogfood evidence
into a release a new user can actually adopt. Beta.1 is not a feature expansion
line. It is the adoption freeze for the v0.41.0 Web Components fullstack
framework proof.

The public product sentence stays:

```text
openElement = Web Components Fullstack Framework + Basic Element
supporting packages = Protocols + UI + official stack adapters
```

Natural-language positioning also freezes:

> OpenElement is a Web Components-native fullstack framework with a JSX-first
> Basic Element authoring layer.

Beta.1 succeeds when a new user can create, run, inspect, build, test, and
deploy a starter without needing historical roadmap knowledge or maintainer
context.

## Workstreams

### A. Five-Minute Starter Path

- `@openelement/create` emits the current product doctrine and npm-first import
  shape.
- A generated starter runs `deno task dev`, `deno task build`, and the local
  smoke checks from a clean directory.
- Starter docs show one happy path first: page, layout, Web Component, API
  route, SSG/SSR output, and deploy proof.
- Starter output avoids archived package names, old four-product language, and
  alpha-only internal import paths.

### B. Public API And Package Truth

- `README.md`, `README.zh.md`, `docs/current/PACKAGE_SURFACE.md`, website API
  pages, npm package metadata, and release notes agree on product status and
  package roles.
- Product packages are described as `@openelement/app`,
  `@openelement/create`, and `@openelement/element`.
- Supporting packages are described as UI, Protocols, SSG, adapter-vite,
  router, signal, content, and core according to the current package surface.
- Any deep import shown publicly has a matching export and a test or package
  surface check.
- Public docs label surfaces as stable-candidate, alpha, internal, supporting,
  adapter, dogfood, or infrastructure before stable v0.41.0 is cut.
- `@openelement/app`, `@openelement/create`, and `@openelement/element` are the
  stable-candidate product surfaces unless a beta.1 review explicitly demotes
  one.

### C. Website Adoption Experience

- The website answers four questions in the first path through the site:
  why openElement, how to start, what the public API is, and where it differs
  from Lit, Stencil, Enhance, Astro, and Fresh.
- The homepage, Getting Started, Architecture, API Reference, Roadmap, and
  docs landing page use the same v0.41.0 ladder.
- Logo, favicon, header, footer, dark/light modes, and mobile header are release
  blockers. The brand mark must never be covered by text or navigation.
- The website avoids decorative claims that are not backed by gates, examples,
  package exports, or release evidence.
- Website pages explain that dogfood apps validate OpenElement but do not define
  OpenElement.

### D. Competitor Positioning

- Lit is documented as a Web Components authoring library.
- Stencil is documented as a Web Components compiler/design-system production
  tool.
- Enhance is documented as the closest HTML-first full-stack Web Components
  peer.
- Astro and Fresh are documented as adjacent app/content frameworks, not
  Web Components-first fullstack competitors.
- The comparison should be respectful, practical, and focused on user choice,
  not winner-take-all rhetoric.

### E. Release Truth

- GitHub release notes, npm package metadata, docs, website, changelog, roadmap,
  and `docs/status/STATUS.md` agree that v0.41.0 is a stable proof of the
  Web Components fullstack framework plus Basic Element product line.
- AutoFlow release evidence includes docs truth, package surface, starter,
  website, third-party WC, Reader, and Mastodon Desktop dogfood gates.
- Deno toolchain truth is resolved: `.dvmrc` is pinned to stable `2.9.0`, README,
  CI setup, release notes, and the starter path all converge on the same pinned
  stable Deno version. Canary is documented only as an exception for Deno Desktop
  preview features.

### F. Governance And Dogfood Boundaries

- AutoFlow3, docs truth, workflow gates, and release evidence are documented as
  infrastructure.
- Reader and Mastodon Desktop are documented as dogfood evidence, not product
  lines.
- Any reusable governance surface is described as future infrastructure, not as
  part of the Web Components framework promise.

## Acceptance

- [ ] A new user can create and build a starter in five minutes from the public
      docs path.
- [ ] Public docs and website use only the two-product doctrine.
- [ ] API reference and package surface docs agree with current exports.
- [ ] Website header/logo renders correctly on desktop and mobile in light and
      dark mode.
- [ ] Lit, Stencil, Enhance, Astro, and Fresh positioning is clear and current.
- [ ] Stable-candidate, alpha, internal, supporting, adapter, dogfood, and
      infrastructure labels are visible in docs where they affect user choice.
- [x] Deno toolchain truth is not ambiguous: stable primary (2.9.0) with canary
      documented only as a Deno Desktop preview exception.
- [ ] Alpha.6 and alpha.7 evidence is linked from the stable v0.41.0 release
      story without turning beta.1 into a feature train.

## Non-Goals

- No new server/data/forms/session/cache primitives.
- No authenticated Mastodon client work.
- No Studio, plugin marketplace, or Hub product launch.
- No new registry strategy beyond npm-first release truth.
- No React/Vue/Svelte adapter expansion.
