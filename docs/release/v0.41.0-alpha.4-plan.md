# v0.41.0-alpha.4 Version Plan - openElement Components in Fresh

## Objective

Prove that openElement components can be consumed as npm packages inside a
third-party full-stack framework, specifically
[Deno Fresh](https://fresh.deno.dev/).

This is the inverse direction of v0.41.0-alpha.3:

- alpha.3: third-party Web Components inside the openElement framework.
- alpha.4: openElement components inside a third-party framework.

This release requires a lightweight client runtime that can boot openElement
components without the full `@openelement/element` framework stack. The
`@openelement/core/hydrate` subpath extracted in v0.41.0-alpha.2 is the
foundation.

## Why Fresh?

Fresh is Deno-native and islands-based, which aligns with openElement's
Deno-first development toolchain and island hydration model. If openElement
components work in Fresh, the same runtime pattern can be adapted to other
frameworks (React, Vue, etc.) later.

## Governance

- No public API breakage unless explicitly listed in **Accepted breaking
  changes**.
- All changes must pass the standard CI gate set.
- E2E regression is a release blocker.
- Merge and publish follow the standard AutoFlow3 release workflow: `dev` PR
  green -> merge to `main` -> wait for `main` CI -> approved
  `autoflow:release --to 0.41.0-alpha.4` / release dispatch -> npm publish with
  provenance -> post-publish npm consumer smoke.

## Workstreams

### v0.41.0-alpha.4 - Lightweight Client Runtime

Create a minimal runtime that can boot openElement components in any standard
browser environment, given only the SSR output and the component class.

- [x] Define the runtime API surface. Recommended shape:
  - `hydrateOpenElement(root: ParentNode, options?: { registry?: CustomElementRegistry })`
  - `disposeOpenElement(root: ParentNode)`
- [x] Implement the runtime in `@openelement/core/hydrate` (or a new
      `@openelement/client-runtime` package if coupling is too high).
- [x] The runtime must:
  - Scan for declarative shadow DOM templates created by openElement SSR.
  - Instantiate `OpenElement` subclasses and attach them to existing shadow
    roots.
  - Hydrate `data-signal-*` markers using `HydrationScope`.
  - Initialize the context registry so `consumeContext` / `provideContext` work.
  - Clean up effects and event listeners on disposal.
- [x] Keep the runtime dependency graph small: ideally only `@openelement/core`,
      `@openelement/signal`, and `@openelement/protocol`.

### v0.41.0-alpha.4 - Fresh Example Project

- [x] Create `examples/open-element-in-fresh/` with:
  - A Deno Fresh project structure.
  - A route that SSRs an openElement component.
  - An island that hydrates the component on the client using the lightweight
    runtime.
- [x] Verify:
  - SSR output contains the correct declarative shadow DOM template.
  - Browser upgrades the component correctly.
  - Signal-driven reactivity works after hydration.
  - Context works across nested openElement components.
  - The component responds to user interaction.

### v0.41.0-alpha.4 - Documentation

- [x] Write `docs/integrations/open-element-in-fresh.md`.
- [x] Document how to load the client runtime in a Fresh island.
- [x] Document limitations:
  - openElement JSX transform must be configured for the component package
    build.
  - `defineElement` auto-registers `customElements.define`; in Fresh this should
    happen on the client, not during SSR.
  - Third-party framework routers may require explicit disposal on navigation.

### v0.41.0-alpha.4 - Release Gate

- [x] Add PR-level Fresh integration evidence:
  - committed `examples/open-element-in-fresh/fresh.gen.ts` so a clean checkout
    has the Fresh route/island manifest needed by `dev.ts` and `main.ts`;
  - Fresh island dynamically imports `@openelement/core/hydrate` and calls the
    real `hydrateOpenElement`, not a local reimplementation;
  - Fresh island disposes the returned hydration cleanup function on unmount,
    including the async import race where unmount happens before the imports
    resolve;
  - Cloudflare Pages preview and both `autoflow-ci` jobs passed on PR #111.
- [x] Add runtime regression coverage for TreeWalker scanning,
      `template.content` fallback, disposer lookup, and non-browser RAF absence.
- [x] Harden Preact island smoke DOM stubs so insertion/removal behavior tracks
      real DOM parent/child semantics.
- [x] Exercise Preact `clientActivate()` hydrate/render paths without
      catch-and-ignore test behavior.
- [x] After merge, run the release workflow from `main` and record npm publish +
      post-publish npm consumer smoke evidence before marking alpha.4 released.

### v0.41.0-alpha.4 - Preact Island Proof

`@openelement/app/preact` has been available since alpha.1 but lacks independent
verification. Prove that a real Preact component can render inside an
openElement island and react to signal-driven state.

- [x] Create a minimal example: an openElement app with a Preact island
      component.
- [x] Verify: the Preact component renders on SSR and hydrates on client.
- [x] Verify: the Preact component reacts to openElement signal state changes.
- [x] Verify: the Preact island is cleaned up on dismount.
- [x] Add a smoke test that fails the release if the Preact bridge breaks.
- [x] Document interoperability boundaries: what works, what doesn't.

## Long-Term Follow-Up

After alpha.4, consider generalizing the client runtime for:

- React (via `useEffect` disposal)
- Vue (via `onUnmounted` disposal)
- Other islands-based frameworks

## Next Version Notes

alpha.5 should stay focused on SPA mode + Deno Desktop shell proof. Do not pull
React/Vue adapters into alpha.5 unless the alpha.4 runtime contract breaks under
SPA navigation. Any wider adapter work belongs in a later interop hardening line
after beta.1 surface freeze planning.
