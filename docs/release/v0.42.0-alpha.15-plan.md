## Context you must internalize before touching anything

Alpha.14 plus the 2026-08-04 simplification sweep (commits `49d8ce09`,
`d72b8c54`, `74cd6825`, `1ca1a43a`, `c0569fc8`, `f618ed70`) already delivered:

re-verify before editing anyway; the audit trail shows these claims rot fast.

Hard constraints (violating any of these breaks consumers or gates):

1. **Published packages** (`packages/adapter-vite/src`, `packages/create/src`)
   are cross-runtime (Node 18+/Deno/Bun). Only Web/ES globals, `node:` specifiers
   and `npm:` dependencies are allowed there. NO `jsr:` imports (breaks packed
   npm installs, #886), NO `Deno.*` (breaks Node consumers). `element/ui/app`
   src are pure Web standard, enforced by `deno task deno-api:check`.
2. **`tools/project-constants.ts` must stay free of jsr:/npm: imports** — it is
   loaded by Nitro/jiti under Node
   (`packages/adapter-vite/__fixtures__/nitro-proof/nitro.config.ts`).
3. Root `deno.json` import-map entries `nitro` and `@rollup/plugin-terser` look
   unused but are load-bearing (critical-paths probe; nitro workers preset
   `require()`s terser at build time). Do not remove them.
4. Deno is pinned to **2.9.0** via `.dvmrc` (dvm/mise). `deno fmt` output
   differs across patch versions — running fmt under any other version
   introduces drift the next pinned run will revert.
5. GitHub auth: `gh` must be logged in (issue comments/closures are part of
   every work package's acceptance).
6. Do NOT create tags, publish to npm, or run any `autoflow:*release*` /
   `publish:npm*` command without the explicit human checkpoint in WP6.

## Execution protocol (applies to every work package)

- One commit per issue (or explicitly bundled pair), conventional-commit style,
  on `main` (current maintainer workflow commits to main directly).
- After each package: `deno fmt` (changed files), `deno lint`, package tests,
  then the relevant gates. Full-suite command: `deno task test`.
- When an issue's premise turns out to be stale or wrong, comment the evidence
  on the issue and close/skip it — do not invent work to satisfy the letter of
  a stale issue.
- Never refactor beyond the issue's scope. No drive-by reformatting.
- Every closed issue gets a closing comment with file:line evidence.

## WP1 — P1 correctness: #897 SPA router URLPattern fallback

**Issue**: `packages/app/src/internal/router/client-router.ts:103-111`
(`compiledPatternFor`) calls `new URLPattern(...)` unconditionally; Firefox
(lacks URLPattern) gets broken SPA routing with no fallback or warning.

- [ ] Implement a runtime fallback: feature-detect `typeof URLPattern`. When
      absent, compile the route pattern to an equivalent RegExp-based matcher.
      The declaration-ordered trie and `matchRouteLinearForTests`
      (`client-router.ts:220`, test-only) show the intended matching semantics —
      the fallback must produce identical match results for the existing route
      pattern syntax used in tests.
- [ ] Emit exactly one dev-mode warning when the fallback engages.
- [ ] Tests: pattern-compile parity between URLPattern and fallback paths
      (params, wildcards, optional segments as already covered by existing
      router tests — reuse those fixtures against both implementations).
- [ ] Gates: `deno test -A packages/app`, `deno task test:e2e:browser-smoke`
      if Playwright browsers are installed locally; otherwise note CI coverage.
- [ ] Close #897 with evidence.
