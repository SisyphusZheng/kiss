# Migrating to 0.42.0 (WC light fullstack)

> Status: shipped migration note for the 0.42.0 stable cut (2026-08-15).
> Upgrade proof: fresh byte-level diff of the same scaffolded static project
> built on npm `0.41.2` and on the 0.42 stable code line (2026-08-15;
> byte-identical pages and content artifacts, zero source changes — the only
> user-visible markup delta is the #960 wrapper on shape-1 pages, and the
> only tree-shape delta is the #953 `dist/server` removal). Earlier proof:
> [`v0.42.0-alpha.13-static-upgrade-proof.md`](./v0.42.0-alpha.13-static-upgrade-proof.md).

`0.42.0` is **WC light fullstack**: the request-time Application Loop
(ADR-0120) frozen on top of the untouched 0.41.x static freeze (ADR-0119).
What ships: dynamic `loader`/`action` routes, no-JS + enhanced form loops,
`build → start`, fail-closed static prerender, default same-origin CSRF on
generated action POSTs, login via recipe. What does **not** ship
(ADR-0122 §5): framework session/flash, cache/ISR, streaming SSR,
performance SLOs, the third-party WC SSR corpus (0.43), production runtime
recovery (0.44), auth packages.

## Pure-static sites (0.41.x) — zero-cost upgrade

Change the `@openelement/*` version specifiers (the generated starter pins
three: app, adapter-vite, element) from `0.41.x` to `0.42.0` and rebuild.
**No source, config or route changes are required.** The static output
contract is frozen under ADR-0119 and untouched by the 0.42 line.

Proof: the same scaffolded static project built against npm `0.41.2` and
against the 0.42 stable code line produces byte-identical pages, content
artifacts and manifests (modulo the per-build `builtAt` timestamp in
`island-manifests/*.json`); only the framework-emitted runtime bundles
(island chunks, island loader, server entry) differ, carrying the alpha
line's protocol hardening — see the upgrade proof linked above.

Verify after upgrading:

1. `deno install` (clean lockfile refresh) and `deno task build`; pages,
   `search-index.json` and assets render identically.
2. Dynamic-route render failures still fail the build by default
   (fail-closed prerender, unchanged since 0.41 alpha.18).
3. `isr-manifest.json` continues to be emitted for forward compatibility
   but stays **inert** on 0.42 — `revalidate` does not enable caching
   (VERSION_PLAN "ISR status (0.42)").

## SPA projects (0.41.x)

Nothing to migrate. The SPA semantics of `defineApp` are inside the
ADR-0119 freeze and the client-side chain is unchanged; the request-time
loop is additive, not a rename or a replacement. Upgrade the version
specifiers and rebuild as above.

If you want request-time behavior later, it is opt-in per route:
`renderIntent: { mode: 'dynamic' }` plus a `loader` (and optionally an
`action`) on a `definePage`. Pages with actions cannot be prerendered — a
route module exporting an action without `mode: 'dynamic'` fails the build,
by design.

## Apps adding login (better-auth)

Login on 0.42 is a **recipe**, not a framework API
([`docs/integrations/better-auth.md`](../integrations/better-auth.md)):
read the session in loaders from the standard `Request` headers, mount
better-auth's handler as an API route, authorize inside actions.
Framework-owned session/flash is a 0.44 topic and is not a prerequisite for
shipping signed-in apps on 0.42.

One interaction to know: generated **action POST** handlers reject
cross-site browser requests fail-closed (`Sec-Fetch-Site`/`Origin`,
ADR-0121). This applies to framework-generated action endpoints; your
better-auth API routes are yours to guard. Non-browser clients can opt out
via `OPEN_ELEMENT_DISABLE_CSRF=1` (documented escape hatch — do not use it
to weaken browser-facing deployments).

## Request-time adopters (already on the 0.42 alpha line)

The frozen semantics at 0.42.0 are the ones the alphas shipped: the
loader/action signatures, the `fail()`/`redirect()` algebra and their HTTP
encodings (422 with error data, 3xx whitelist, PRG revalidation), the
`x-openelement-action` negotiated channel, the morph client contract, the
CSRF default, and `build → start` first-mile semantics (ADR-0122 §1–§4).
Post-freeze changes to any of these require an amendment ADR.

## alpha.17: definePage routes register under the route-path tag (#960)

**Breaking SSR markup change on the unfrozen alpha line.** Route modules
whose default export is `definePage(...)` now always register the page class
under the route-path-derived fallback tag (`app/routes/index.tsx` →
`index-page`); the `export const tagName` on such a route is ignored for
registration and only names a content element (ADR-0128).

Who is affected:

- **Shape-1 pages** (the starter pattern: `export const tagName` +
  `defineElement(tagName, …)` content element + a definePage render
  returning `<that-tag/>`) gain the fallback-tag page element as an **outer
  wrapper** with its own DSD shadow root around the content element:
  `<home-page>…` becomes
  `<index-page><template shadowrootmode="open"><home-page>…</home-page></template></index-page>`.
  Hydration markers are unchanged (they pair per element), and the morph
  client is tag-agnostic at the document root, so no-JS and enhanced form
  loops behave identically. **User CSS that targeted the old root tag**
  (e.g. `home-page { … }` in a global stylesheet) must target the new
  fallback tag (`index-page`) or the content element.
- Pages that previously combined a same-tag self-registered content element
  with a definePage render depending on `request`/`useActionData()` now
  render **correctly** — before alpha.17 the content element won the
  registration and the page render was silently bypassed.
- **Plain element routes** (no `definePage`, default export is an element
  class) are untouched: their `tagName` export remains the registration tag.

Migration: none required for source code — the starter shape keeps working
unchanged. If a definePage route exports `tagName` without ever using the
tag (no `defineElement(tagName, …)` call, no `<tag/>` in the render), the
scanner logs a one-time note that the export is ignored; deleting the export
is cosmetic.

**Residual corner (hard failure since 0.43).** If the content element's tag
_equals_ the route's fallback registration tag (e.g. `app/routes/contact.tsx`

- `tagName = 'contact-page'` + `defineElement('contact-page', …)`), the
  self-registered content element would still shadow the page class under the
  #952 ownership rule and the definePage render would be bypassed. On 0.42.x
  the scanner warned once per route; from 0.43 the scanner **fails the
  build** with the rename guidance (#971) — give the content element a
  distinct tag (the shape-2 pattern, e.g. `contact-form-view`).
