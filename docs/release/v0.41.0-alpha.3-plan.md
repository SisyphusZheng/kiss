# v0.41.0-alpha.3 Version Plan - Cross-Framework Web Components Integration

## Objective

On the stable signal-DOM architecture landed in v0.41.0-alpha.2, prove that the
openElement full-stack framework can consume mature third-party Web Components
and that openElement packages remain pure ESM / pure ECMAScript / modern Web
Standards artifacts.

This release answers three questions in order:

1. Can production-grade Web Components libraries be used directly inside an
   openElement app?
2. What is the documented interoperability contract between openElement
   components and standard Custom Elements?
3. Do the npm artifacts satisfy strict pure-ESM / pure-ECMAScript / modern
   W3C/WHATWG Web Standard API quality gates?

## Governance

- No public API breakage unless explicitly listed in **Accepted breaking changes**.
- Implementation priority is:
  1. Native Web Platform / W3C / WHATWG / ECMAScript APIs first, especially for
     runtime-free and browser-facing packages.
  2. Deno-first tooling and server/build integration before Node-specific
     implementations.
  3. Mature, high-quality open source libraries before custom rewrites.
  4. Custom implementation only when the behavior is core to openElement, the
     native/Deno/library option cannot satisfy the contract, or dependency risk
     is higher than the local code.
- All changes must pass the same CI gate set as alpha.2:
  `fmt:check`, `lint`, `typecheck`, `test`, `graph:check`, `arch:check`,
  `docs:check-*`, `repo:hygiene`, `workflow:check`, `build`, `consumer:packaged`,
  `test:e2e`, `autoflow:ci`.
- E2E regression is a release blocker.

## Workstreams

### v0.41.0-alpha.3 - Mature WC Library Direct Use

Validate that openElement apps can consume production-grade third-party Web
Components with zero or minimal adapter code. The goal is to use mature Custom
Elements directly instead of rewriting design-system components inside
openElement. Target libraries:

**Primary targets:**

- **Lit** — the component authoring framework underlying the two libraries below.
- **Shoelace** (`@shoelace-style/shoelace`) — design-system library based on Lit.
- **Material Web Components** (`@material/web`) — Google design system based on Lit.

**Optional targets (if time permits):**

- **FAST** — prove interoperability with a non-Lit base.
- **Stencil compiled output** — prove compiled-to-CE artifacts work.

For each primary target, verify:

- [x] `npm install` works in an openElement starter project.
- [x] The library's components render in an openElement JSX route.
- [x] Components serialize correctly during openElement SSR/SSG: tag names,
      attributes, children, and slots are preserved. Declarative shadow DOM is
      required only when the third-party library natively supports it; otherwise
      light-DOM/client-upgrade fallback is acceptable and documented.
- [x] Components hydrate correctly on the client and remain interactive.
- [x] Events emitted by third-party components are received by openElement handlers.
- [x] Slots provided by openElement parents are rendered by third-party components.
- [x] CSS custom properties / theme tokens flow between openElement and the third
      party (at minimum, no visual breakage on light/dark theme switch).
- [x] Each verified library has a smoke test that fails the release if it breaks.

Files to add/modify:

- `tools/third-party-wc-smoke.ts`
- `deno task third-party-wc:smoke`
- `docs/integrations/using-third-party-web-components.md`

### v0.41.0-alpha.3 - Cross-Framework WC Capability Benchmark

Document and test the interoperability contract between openElement and standard
Custom Elements. This is the theoretical counterpart to the practical validation
above.

- [x] Document the contract:
  - openElement components are standard CEs (`OpenElement extends HTMLElement`).
  - openElement SSR serializes only light DOM for standard CEs (attributes,
    properties, children, slots); their shadow roots are created by the browser.
  - openElement signal binding applies only to `OpenElement` components. Third
    party CEs manage their own reactivity.
  - `customElements.define` is shared; tag-name collisions are the user's
    responsibility.
- [x] Add a minimal unit test:
  - An openElement component contains a Lit component; verify lifecycle, events,
    and slots.
  - A Lit component contains an openElement component; verify the same.
- [x] Add a "when to use what" guide:
  - Use `defineElement` when you need signal-driven JSX, DSD hydration, or
    openElement context.
  - Use third-party CEs directly when the library already provides the component.
  - Do not rewrite mature third-party components unless openElement needs a
    different contract that the library cannot provide.

- `docs/integrations/web-components-interop.md`
- `packages/core/__tests__/event-hydration.test.ts`
- `packages/core/__tests__/jsx-render-dom.test.ts`

### v0.41.0-alpha.3 - Pure ESM / Pure ECMAScript / Web Standards Quality Gates

openelement is a pure ESM / pure ECMAScript project. We do not ship CommonJS
builds and we do not support legacy Node.js resolution. Add automated gates that
fail the release if artifacts violate this contract.

For runtime-free and browser-facing packages, "pure ECMAScript" means Web
Standard APIs first: no `Deno.*`, no `node:*`, and no Node-only globals in the
published runtime surface. "Modern Web Standards" means relying on native
W3C/WHATWG/Web Platform APIs for browser-facing runtime behavior: Custom
Elements, `HTMLElement`, Shadow DOM, DOM Events, `CustomEvent`,
`AbortController`, `URL`, `URLSearchParams`, `fetch`, Streams, `FormData`,
`structuredClone`, and `queueMicrotask` before custom platform wrappers. For
build/server glue packages (`ssg`, `content`, `adapter-vite`, `create`),
Deno-first platform APIs are allowed and preferred over Node-specific
implementations, while the npm artifact must still expose ESM exports.

**Tool-based gates:**

- [x] Run `publint` against every npm tarball produced by `deno pack`.
- [x] Run `attw` against every npm tarball in an ESM-only-compatible
      configuration. We only care about ESM resolution and type correctness.
- [x] Fail the release if either tool reports errors for any package.
- [x] Keep JSR checks non-blocking unless a later ADR restores JSR as a required
      release gate.

**Custom static scans (on extracted tarballs):**

- [x] No `require(` / `module.exports` / `exports.` / `__dirname` / `__filename`.
- [x] No Node-only globals in runtime-free/browser-facing packages: `process`,
      `Buffer`, `setImmediate`, `clearImmediate`.
- [x] No `Deno.*` API in runtime-free/browser-facing packages.
- [x] Entry files use standard ESM syntax (`import` / `export`).
- [x] `package.json` has `"type": "module"` and no `"main"` pointing to CJS.

**Native Web Standards checks:**

- [ ] Runtime-free/browser-facing public code uses native W3C/WHATWG/Web Platform
      APIs for Custom Elements, DOM events, URL handling, fetch/cancellation,
      streams, form data, cloning, and microtask scheduling.
- [ ] Any custom wrapper around a standard Web API has a documented reason:
      compatibility, SSR isolation, package boundary, or a stable openElement
      contract that the native API alone cannot provide.
- [ ] Mature, standards-compatible open source libraries are preferred before
      local rewrites when a required behavior is not native.

**Runtime smoke:**

- [ ] Load each package via Node ESM, Deno `npm:`, and jsDelivr CDN and confirm
      `import` succeeds without falling back to CJS.

**Documentation:**

- [ ] Update `ADR-0108-deno-native-npm-distribution.md` with the pure-ESM
      rationale, Deno-first/runtime-free package boundary, and modern Web
      Standards API priority if needed.

- `tools/autoflow/policy.ts`

## Deferred to v0.41.0-alpha.4

### v0.41.0-alpha.4 - openElement Components in Fresh

Prove that openElement components can be consumed as npm packages inside a
[Deno Fresh](https://fresh.deno.dev/) application. This is the inverse direction
of alpha.3: instead of third-party CEs inside openElement, it is openElement
components inside a third-party framework.

This requires a lightweight client runtime that can boot openElement components
without the full `@openelement/element` framework stack. The alpha.2
`@openelement/core/hydrate` subpath is the foundation.

See `docs/release/v0.41.0-alpha.4-plan.md`.
