# v0.43.3

**Renderer-owned light DOM hydration and the robustness audit closure for the
0.43 maintenance line.** This patch corrects light-mode SSR hydration to
activate the server-rendered subtree in place and closes the final adversarial
audit of the frozen line. It adds no public option, lifecycle hook, package,
migration, or breaking change.

## What changed from v0.43.2

### Light-mode in-place activation (#1148, ADR-0142)

- `renderMode = 'light'` SSR output is now the authoritative initial DOM. On
  client upgrade, a server-rendered light subtree is activated in place by
  binding its existing event, signal, attribute, and `<Show>`/`<For>` markers —
  no nodes are replaced. Node identity, focus, selection, live form values,
  nested custom-element instances, and pre-upgrade interaction targets survive
  the upgrade.
- Light-layer hosts carry the internal `data-oe-light` SSR provenance marker.
  Hosts without it (empty `createElement` hosts, or pre-v0.43.3 cached HTML)
  keep the previous clear-and-render CSR behavior, so old output degrades
  gracefully instead of mis-binding.
- Nested light-mode hosts are scoped: a parent's activation walk prunes a
  nested host's rendered subtree, the nested instance hydrates with its own
  scope, and parent activation never replaces the child instance. Light roots
  additionally validate the exact `data-eid` marker multiset (new `marker-id`
  mismatch reason), not just marker counts.
- Marker or branch mismatches keep the existing structured
  `OPEN_ELEMENT_HYDRATION_MISMATCH` diagnostic — wording is now correct for
  light-host roots — and degrade to a clean client render. The Chromium
  DSD-only layout fix is no longer scheduled for light hosts.
- Pre-hydration click capture/replay now covers light-mode hosts: the latest
  pre-upgrade click replays exactly once after activation, and only when the
  recorded target remains connected inside the same host (supersedes the #1067
  skip). Explicit `update()` remains a full client re-render, and the
  Shadow/DSD default is unchanged.

### Robustness adversarial audit closure (#1146)

- The six required coverage areas — Node bridge, Preact lifecycle, router
  disposal, action wire parity, Starter failure matrices, and repeated-cycle
  resource growth — are now exercised by committed, reproducible tests with a
  per-case evidence record
  (`docs/audit/2026-08-26-v0.43.3-robustness-adversarial-audit.md`).
- `writeWebResponse` no longer misses a client disconnect that predates it: an
  entry-time terminal-state check cancels the body and cleans up listeners
  instead of pumping into a dead socket (#1152).
- A never-settling request-body `cancel()` no longer blocks listener cleanup on
  the disconnect path (#1154).
- The Starter Notes island's 401 → refresh → retry-once pipeline is extracted
  into the injectable `fetchNotesSnapshot` helper, making the wiring
  unit-testable without a browser (#1153).
- New locked coverage includes hash-mode guard disposal, dispose
  mid-redirect-chain, synchronously-throwing guards, Preact hydration over real
  SSR children, native-channel action parity for unserializable payloads,
  dishonest `Content-Length` and handler-level stalled-body cases, upload
  double-finalize races, and abandoned-intent expiry convergence.

### External application evidence (authoring-fitness slice)

- The real-application evidence source previously codenamed `nextCrm` is
  superseded by the **Electrical Export Sales SaaS** authoring-fitness slice.
  The slice first reproduced the #1148 defect on exact published `0.43.2`
  artifacts — typed-value/focus/selection loss, nested-instance re-creation,
  and a lost pre-upgrade click, each with Playwright trace/video/DOM-identity
  evidence in Chromium, Firefox, and WebKit — and then re-ran the same
  scorecard (OE-AF-01…04) against the coherent five-package `0.43.3` candidate
  set with all four specs passing.

### Zag composition experiment (#1149, non-blocking)

- The `@zag-js/combobox` + `@zag-js/vanilla` + Open Props spike composed
  successfully with OpenElement TSX/SSR and both render modes in the
  request-time fixture (9 e2e tests × 3 browsers). Evidence and bundle cost are
  recorded in `docs/evidence/2026-08-26-zag-composition-spike.md`. Per the
  issue's outcome rules this does not activate a public contract or unblock
  #1150; that decision waits for real-application evidence under ADR-0140.

## Compatibility and upgrade notes

1. Bump all five `@openelement/*` packages together to `0.43.3` and refresh
   the lockfile. The Node 24+ generated-server floor is unchanged.
2. No public export was removed or added. Existing 0.43.2 applications require
   no source migration. ADR-0142 is a compatibility correction to the existing
   light-mode SSR/CSR promise under the ADR-0140 classification table.
3. Light-mode SSR output gains one internal marker attribute (`data-oe-light`)
   per host. Light-mode connections keep firing `onCsrRendered()` — on both the
   activation and CSR paths — so existing light-mode init code keeps a single
   hook; `onDsdHydrated()` remains Shadow/DSD-only.
4. The Supabase starter still has 23 immutable migrations. This patch adds no
   migration and requires no remote schema apply.

## Qualification

- The root test task passes 1,765 framework/tool/example tests plus 150 tests
  under the starter's independent configuration.
- Light-mode in-place activation is covered by contract unit tests
  (`packages/element/__tests__/light-dom-activation.test.ts`) and by real
  SSR → delayed-upgrade e2e in Chromium, Firefox, and WebKit
  (`www/e2e/light-mode-activation.spec.ts`).
- The #1146 audit matrix records PASS/FAIL per case with exact commands,
  iterations, thresholds, and raw evidence paths; both confirmed defects were
  fixed and their evidence tests flipped to PASS unchanged.
- The authoring-fitness slice ran twice per spec: expected-failure baseline on
  packed `0.43.2` artifacts, then PASS on the packed `0.43.3` candidate set
  (SHA-256-locked tarballs).
- Full comparison:
  https://github.com/open-element/openelement/compare/v0.43.2...v0.43.3

External provider claims remain deliberately narrow: this patch does not claim
new real Stripe delivery, production Cloudflare deployment, SMTP/OAuth, or
malware-scanner evidence. The audit ran loopback-only with in-process fixtures
and local servers.
