# v0.44 Alpha/Beta Autonomous Execution Plan

## Purpose

This plan turns the Version Plan and GitHub graph into deterministic work waves for the
ADR-0146 thinker/implementer/verifier loop. It schedules work; it does not replace issue
acceptance criteria or version promotion authority.

## Work-packet size

One loop owns one independently testable issue slice, normally one unchecked deliverable
plus its tests and documentation. A packet should fit one K3 session. Split it when:

- it owns more than one architecture boundary;
- its required gates cannot be stated as one coherent matrix;
- it edits unrelated packages;
- a partial result can be accepted without pretending the entire issue is complete.

An issue closes only after all its slices and issue-level acceptance criteria pass.

## Per-issue loop

1. Reconcile state, branch, dirty files, issue status and blockers.
2. Select one acceptance slice and assign a loop ID such as `a0-001`.
3. Write `dispatch.md` from the evidence template.
4. Start a new K3 implementer session with the pinned profile and packet.
5. Let K3 execute test-first implementation and bounded repair, maximum five internal
   attempts.
6. Sol inspects every changed file and rejects scope drift, fallback architecture,
   hidden compatibility paths or unsupported claims.
7. Sol independently runs the packet harness.
8. On failure, write `review.md`, issue a repair packet to a new or explicitly resumed
   implementer session, and repeat. Sol does not repair product code itself.
9. On pass, write `result.json` and `summary.md`, update the state and issue checklist,
   then create the scoped commit/PR actions permitted by the bootstrap prompt.
10. Select the next ready slice without waiting for a conversational acknowledgement.

## Version-closure loop

After every alpha or beta issue set is green:

1. freeze the candidate commit SHA and package/artifact fingerprints;
2. write a closure packet containing the complete version exit criteria, issue evidence,
   changed public surfaces and mandatory commands;
3. start a **fresh** K3 verifier session using the verifier profile;
4. the verifier derives a test plan before accepting existing coverage, adds missing
   tests/fixtures only, and runs the candidate matrix;
5. production-code changes by the verifier invalidate the run;
6. FAIL returns to an implementer repair loop, after which another fresh verifier runs;
7. PASS is followed by Sol independently rerunning the closure harness and checking
   packed artifacts/GitHub truth;
8. write the human decision packet and set state to `AWAITING_HUMAN_GO`;
9. never tag, publish or promote until the human names the exact approved SHA.

## Repair and retry limits

- K3 implementer: at most five repair attempts for one packet.
- Tool/network transient: retry twice, then mark the exact command BLOCKED.
- K3 release verifier: one run per candidate SHA; any code repair creates a new SHA and
  requires a new verifier session.
- Same root cause repeated across three outer loops: record a design escalation for Sol.
- Architecture ambiguity: stop immediately; do not let either K3 role choose policy.
