# v0.44 Alpha/Beta Autonomous Execution Plan

## Purpose

This plan turns the Version Plan and GitHub graph into deterministic work waves for the
ADR-0146 thinker/implementer/verifier loop. It schedules work; it does not replace issue
acceptance criteria or version promotion authority.

## CI evidence tier authority

The loop contract selects only packet-specific RED/GREEN commands plus the fast push
tier for implementation, packet-specific deterministic replay for review, one exact-SHA
full CI matrix on the PR (`deno task autoflow:ci`), and version-only/adversarial work
at release closure. The full authority table lives in the agent loop SOP ("CI evidence
tiers"); the machine-readable contract lives in `tools/autoflow/loop-evidence.ts`. No
role may claim a full-matrix PASS from a different SHA, and release closure fails closed
on absent, stale, failing or SHA-mismatched PR CI evidence.

## Work-packet size

One loop owns one independently testable issue slice, normally one unchecked deliverable
plus its tests and documentation. A packet should fit one implementer session. Split it when:

- it owns more than one architecture boundary;
- its required gates cannot be stated as one coherent matrix;
- it edits unrelated packages;
- a partial result can be accepted without pretending the entire issue is complete.

An issue closes only after all its slices and issue-level acceptance criteria pass.

## Per-issue loop

1. Reconcile state, branch, dirty files, issue status and blockers.
2. Select one acceptance slice and assign a loop ID such as `a0-001`.
3. Write `dispatch.md` from the evidence template.
4. Start a new implementer session with the configured profile and packet via
   `deno task v044:role -- implementer`.
5. Let the implementer execute test-first implementation and bounded repair, maximum
   five internal attempts.
6. The thinker inspects every changed file and rejects scope drift, fallback
   architecture, hidden compatibility paths or unsupported claims.
7. The thinker independently runs the packet harness (reviewer replay tier only).
8. On failure, write `review.md`, issue a repair packet to a new or explicitly resumed
   implementer session, and repeat. The thinker does not repair product code itself.
9. On pass, write `result.json` and `summary.md`, update the state and issue checklist,
   then create the scoped commit/PR actions permitted by the bootstrap prompt.
10. Select the next ready slice without waiting for a conversational acknowledgement.

## Version-closure loop

After every alpha or beta issue set is green, starting with `alpha.1` (the `alpha.0`
internal integration baseline receives loop review only):

1. freeze the candidate commit SHA and package/artifact fingerprints;
2. link the exact-SHA PR full-CI result; absent, stale, failing or mismatched evidence
   fails closed;
3. write a closure packet containing the complete version exit criteria, issue evidence,
   changed public surfaces and mandatory commands;
4. start a **fresh** release verifier session using the configured verifier profile via
   `deno task v044:role -- release-verifier`;
5. the verifier derives a test plan before accepting existing coverage, adds missing
   tests/fixtures only, and runs the release-only, adversarial, packed-artifact and
   version-exit checks (it does not replay the PR matrix);
6. production-code changes by the verifier invalidate the run;
7. FAIL returns to an implementer repair loop, after which another fresh verifier runs;
8. PASS is followed by the thinker independently rerunning the closure harness and
   checking packed artifacts/GitHub truth;
9. record the unanimous implementer/release-verifier/thinker GO against the exact
   candidate SHA;
10. execute the authorized release closure: advance `main` to the frozen candidate SHA
    by fast-forward only (`git merge --ff-only`), create and
    push the version tag, publish the npm packages, move the dist-tag, publish the
    GitHub Release, update evidence/issues and advance the execution cursor. For
    `alpha.1` through `beta.2` this bootstrap authorization replaces any human stop;
    the only human GO gate is #1178 RC admission, where the thinker writes the human
    decision packet and sets state to `AWAITING_HUMAN_GO`.

All integration is exact-SHA-preserving and fast-forward-only: `dev` advances to the
proved PR head SHA and `main` later advances to that same frozen candidate SHA via
`git merge --ff-only` (or an equivalent explicit fast-forward ref update), never via
merge commit, squash or rebase and never by force-push. If a fast-forward is
impossible because the base moved, the candidate is stale: refreeze a new candidate
head and require a new exact-SHA PR CI run instead of relabeling old evidence.

## Repair and retry limits

- Implementer: at most five repair attempts for one packet.
- Tool/network transient: retry twice, then mark the exact command BLOCKED.
- Release verifier: one run per candidate SHA; any code repair creates a new SHA and
  requires a new verifier session.
- Same root cause repeated across three outer loops: record a design escalation for the
  thinker.
- Architecture ambiguity: stop immediately; do not let either executor role choose policy.

## Completion handoff

After beta.2 closure, the thinker prepares #1178 with:

- exact candidate SHA and five-package fingerprints;
- alpha/beta closure evidence links;
- public surface diff from 0.43.3;
- browser/runtime/packed-consumer matrices;
- unresolved issue list, which must contain no pre-RC P0/P1;
- explicit RC GO/NO-GO recommendation.

The autonomous Goal then waits for the human RC decision. It does not begin #1179.
