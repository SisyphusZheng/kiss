# OpenElement v0.44 alpha.6 interoperability

Alpha.6 owns the interoperability qualification for issue #1175. The corpus
keeps OpenElement's element model as the host contract: native Custom Elements
are admitted by standards-shaped metadata, while framework-specific behavior
stays inside the fixture dependencies. No adapter is added to Element core.

## Corpus

The deterministic corpus is [corpus.json](../../tests/fixtures/v044-interop/corpus.json).
It exercises one native element and elements authored with Lit 3.3.3, FAST
3.0.2, and Ionic's Stencil output 8.8.18. Each element appears both as a child
of `v044-interop-child-host` and as a direct application dependency. The host
uses a native open shadow root and a default slot.

Every instance is checked for:

- property and attribute behavior;
- custom events;
- light-DOM slot assignment;
- CSS parts and an open shadow root;
- constructor-before-connected upgrade order;
- in-place upgrade identity and pre-upgrade live state.

The same corpus is exercised by the server build, existing authored DOM, and a
freshly created browser DOM for each framework. The CEM artifact at
[compiler-output.cem.json](../../tests/fixtures/v044-interop/compiler-output.cem.json)
is validated as Custom Elements Manifest schema `1.0.0`; its four custom
element tags must match the corpus in order.

## SSR and admission limits

The OpenElement fixture receives its normal SSR output and declarative shadow
DOM. The four foreign elements remain authored light-DOM tags with their
children intact; no foreign tag receives a declarative shadow root.

Foreign elements without a validated SSR capability are admitted as
client-only. The generated admission plan records diagnostic `OEI2001`:

> unknown SSR capability; fail closed to client-only without a compatibility fallback

This is a closed decision, not a framework adapter or a second rendering path.
An explicit `client-only` capability is recorded as `OEI2000`; a validated
`ssr` or `ssr+client` capability is the only route to `OEI1000`.

## Qualification

Run the focused contract tests with:

```sh
deno test --config tests/fixtures/v044-interop/deno.json --allow-read \
  tests/fixtures/v044-interop/qualify-v044-interop.test.ts
```

Run the complete SSR/build/browser qualification with:

```sh
deno run --config tests/fixtures/v044-interop/deno.json \
  --allow-read --allow-write --allow-run --allow-env --allow-net --allow-sys \
  tools/qualify-v044-interop.ts
```

The qualification passes in Chromium, Firefox, and WebKit. The stable result
is recorded in [interop-evidence.json](../../tests/fixtures/v044-interop/interop-evidence.json):
all eight authored instances and four fresh instances pass every probe,
existing nodes retain identity and live state, browser page errors are empty,
foreign SSR admission is client-only, and the OpenElement fixture has DSD.

The initial focused RED was the same test before
`tools/qualify-v044-interop.ts` existed: Deno reported `TS2307` for the missing
qualifier module. The re-audit also produced a focused browser RED when
existing-DOM identity/live-state evidence was required but not recorded; the
fixture now captures it before registration. The focused test is GREEN with
four passing tests, and the full qualification is GREEN in all three browsers.

The fixture app imports only its generated/application entry and the public
framework packages. It does not import `Part`, `Region`, `Signal`, `claim`, or
other runtime internals. Changes are limited to alpha.6's owned fixture,
qualifier, and documentation paths.
