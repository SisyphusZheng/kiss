# v0.44 alpha.7 performance qualification

Issue #1176 owns the internal alpha.7 qualification gate for the frozen v0.44
workspace baseline.

## Scope

This workspace measures the compiler-owned Part Program path end to end:

- serializable Part Program generation
- server serialization
- fresh DOM creation
- existing-DOM claim
- browser continuity checks for claim identity and live state

The benchmark is intentionally narrow. It does not add a compatibility layer, a
fallback renderer, or any contract changes.

## Owned artifacts

- Benchmark runner: `tools/benchmark-v044.ts`
- Acceptance gate: `tools/check-v044-performance.ts`
- Qualification test: `benchmarks/v044/performance.test.ts`
- Fixture inputs: `benchmarks/v044/fixtures.json`
- Static fixture: `benchmarks/v044/static.html`
- Evidence output: `benchmarks/v044/evidence.json`

## Acceptance contract

The gate fails closed unless the report stays within the frozen alpha budgets:

- critical regressions stay at or below 10 percent
- heap growth stays within the configured cap
- retained subscriptions stay at 0
- retained listeners stay at 0
- claim allocations stay at 0
- static runtime bytes stay at 0
- browser page errors stay at 0

The benchmark report for the current owned head records the following evidence:

- candidate interactive Part Program bytes (`interactiveProgramBytes`, excluding
  diagnostic source maps): 3943 versus 4096 baseline
- static runtime bytes: 0
- transferred bytes: 219
- browser matrix: chromium, firefox, webkit
- claim identity preserved: yes
- live value preserved: yes

## Qualified result

The focused test and benchmark both pass on the current head, and the browser
evidence is complete for all three required engines.

# v0.44 diagnostic performance baseline (issue #1219)

This section records the diagnostic baseline required by issue #1219. It is a
measurement record, not a ranking claim; every number comes from an actual run
on the recording machine with full provenance stored next to the results.

## Owned artifacts

- JFB harness and OE keyed implementation: `benchmarks/jfb/**`
- JFB raw results + provenance: `benchmarks/jfb/evidence.json`
- OE microbenchmarks: `benchmarks/v044/micro.ts`
- Micro raw results + provenance: `benchmarks/v044/micro-evidence.json`
- Deterministic harness self-checks: `benchmarks/jfb/harness.test.ts`,
  `benchmarks/v044/micro.test.ts`

## Method summary

- OE granularity: one `jfb-oe-table` component owns the jumbotron and one
  table; rows are plain `<tr>` nodes inside a single keyed `each` region
  (key = row id). One delegated click handler on the table; selection travels
  through row data. No per-row custom elements, no per-row event parts.
- Comparators: stock JFB keyed implementations (vanillajs, preact-signals,
  lit, solid, vue, svelte) fetched unmodified from the pinned JFB commit
  `21d7204da754846fe1402f4437b5b53066f3c34e` with per-file SHA-256
  verification, built out-of-tree with their stock dependency ranges.
- Driver: stock webdriver-ts afterframe semantics
  (`t0 = performance.now(); click; resolve after rAF + MessageChannel task`),
  stock warmup counts, fresh page per measured iteration, 10 CPU iterations
  (stock is 15; recorded as a deviation).
- Browser: Chromium 147.0.7727.15 via Playwright 1.59.1 with
  `--enable-precise-memory-info` and `--expose-gc` for the memory probes.
- Machine: Apple M2, 8 cores, 16 GB, macOS arm64 (Darwin 25.5.0); Deno 2.9.0,
  Node v24.18.0.

## Diagnostic findings (reported, not fixed — out of packet scope)

1. Keyed swap moves 997 DOM nodes for a 2-row swap (Region move is
   O(distance) node-by-node; ~19.9 ms browser median vs 7.85–12.8 ms for
   solid/vanillajs). Algorithmic inefficiency, not a correctness break.
2. OE heap per row is roughly 2.3–5x vanillajs (region entry bookkeeping).
   Memory returns to near-ready after clear (1,400,756 vs 1,219,651 bytes),
   so this is footprint, not a leak. Churn microbenchmark: 0 retained
   subscriptions, 0 retained listeners over 25 x 200-row cycles.
3. Claim is ~2.28x fresh creation in the fake-DOM microbenchmark
   (10.39 ms vs 4.57 ms for the 1k-row table; claim performs 0 allocations).
   Not near full-rerender cost, but above 1x.
4. `tools/benchmark-v044.ts`'s test-only `serializeToHtml` emits
   `[object Object]` for multi-field `each` ival slots. The canonical server
   serializer (`serializeCompiledProgram`) is correct; production SSR output
   is unaffected. The micro suite uses the canonical serializer.

## Microbenchmark headline (fake-DOM, deterministic counts; see micro-evidence.json)

- signal → text part: 0.448 µs/op, exactly 2000/2000 text writes
- signal → attr part: 0.265 µs/op, 2000/2000 attr writes
- signal → prop part: 1.309 µs/op, 1999/2000 value writes (equality guard)
- engine floor (signal write, no part): 0.096 µs/op
- serialize 1k rows: 6.98 ms, 235,946 bytes
- fresh 1k rows: 4.57 ms, 10,031 allocations
- claim 1k rows: 10.39 ms, 0 allocations, claim/fresh 2.275
- partial update (every 10th of 1k): exactly 100 text writes, 0 allocations
- compiler: 8.08 ms median for the JFB component (25 samples), 15,205-byte
  part program, 67,025-byte generated module
